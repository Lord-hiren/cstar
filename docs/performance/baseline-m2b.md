# Pentest M2-2B Performance Baseline

> **Historical record** (`pentest 0.2.0-m2b`, before the garbage collector and
> before the `0.2.1` optimisation lane). Part of the
> [performance documentation](README.md). Current mechanisms:
> [optimization.md](optimization.md).

Recorded by `bench/run-m2b.sh` (results file: `bench/results/m2b-baseline.md`,
run 4 = the recorded baseline). Methodology identical to
`docs/performance/baseline-m1.md`: same machine, same pinning, same 7-rep min/median
protocol, C++ twins with the identical algorithm and byte-identical outputs,
so M1→M2 deltas below are apples-to-apples.

## 1. What the 2B suite adds

M1 had no control flow: its loop workloads were finite *call chains* over
unrolled arithmetic (the honest way to measure M1 codegen, and the source of
its 47–117 s compile cliff). Stage 2B gives the language real `while` loops,
`if/elif/else`, functions/closures, and the full collection set (list, map,
set, tuple, text, bytes). The 10 new cases reuse the exact step counts,
arithmetic, and — for `while_string` — the exact frame structure of the M1
workloads (600,000 appends + 150,000 period-5 resets, peak 72-byte strings),
so every paired row isolates "real loop vs call chain" instead of mixing in
different work.

## 4. Compile time and the run-mode cache

Every case compiles in **1.4–2.0 s** regardless of workload (no superlinear
component; M1 spent 35–117 s on the same workloads via unrolled chains).
`while_int` (278 source bytes): 1835 ms Pentest build vs 209 ms twin.

Cache probe (`run` mode, fresh `XDG_CACHE_HOME`, while_int): cold 2535 ms
(compile + exec) vs warm 1247 ms (exec only) — a 2.0x, because execution
(~1.2 s) now dominates; M1's equivalent probe was 234x (112 s compile vs
0.5 s exec). Cache keyed by sha256(source + compiler version); `build` mode
never caches.

## 5. Before/after vs the M1 baseline (real loops vs call chains)

| Workload | M1 case (median) | 2B case (median) | Runtime ratio | M1 build | 2B build | Build speedup |
|---|---|---|---|---|---|---|
| 12,976,128 int LCG steps | int_loop 531.3 | while_int 1242.3 | 0.43x | 111,785 ms | 1835 ms | **61x** |
| 12,976,128 double steps | float_loop 592.3 | while_float 1235.8 | 0.48x | 117,192 ms | 1726 ms | **68x** |
| 600,000 appends + 150,000 resets | string_ops 88.8 | while_string 169.5 | 0.52x | 35,355 ms | 1854 ms | **19x** |

Two honest headline numbers:

- **Compile: 19–68x faster**, and flat across all workloads — the M1
  superlinear clang cliff (O(K+N) unrolled statements handed to clang) is
  structurally gone: an N-step loop is O(1) statements.
- **Runtime: real loops are 1.9–2.3x slower than M1's call chains on the
  same arithmetic.** M1's chains got their call/return plumbing inlined
  away by clang and paid only ~3.5 runtime ops per step; a 2B `while`
  iteration pays per-iteration bookkeeping: `while_int` emits 8 external
  runtime calls per iteration (2x `pt_guard` reads, `pt_lt`, `pt_truthy`,
  `pt_mul`, 2x `pt_add`, + guard for the counter increment) plus inlined
  `pt_int` re-boxing of loop constants. See §7 for the named fixes.

## 6. Measured optimizations (the baseline doing its job)

The first baseline run exposed `set_ops` at **647x the C++ twin** — three
independent O(size)-per-operation defects in the shared map/set table
machinery, each found by measurement and fixed in the same stage
(every fix re-verified at 268/268 before re-measuring):

1. **`pt_table_first` rescanned from index 0 on every call.**
   `pt_table_delete` tombstones without compacting the insertion-order
   array, so a front-draining `pop()` loop paid Σk ≈ 7e9 scan steps.
   Fixed with a maintained `first` cursor: entries are append-only and
   the cursor only advances, so the advance scan is amortized O(1).
2. **`pt_table_clear_slot` re-homed the whole live run per delete.** The
   forward "re-home until the next empty slot" walk spans the entire
   dense probe run on a packed table — a second Σk. Provably unnecessary:
   `pt_table_find` skips tombstones *and* dead-entry slots, `pt_table_insert`
   probes from the key's home and reuses tombstones in its own chain, and
   the 75%-load rehash guard guarantees `find` always meets an empty slot.
   Deleted slots are now plain tombstones.
3. **`pt_contains` linearly scanned the entry array for map/set
   membership** — it computed the hash and then ignored the slot table.
   Now probes through `pt_table_find` (identical match condition:
   `used && hash == h && total-eq`), same as `pt_set_add`/`pt_map_set`
   have always done.

Ledger (`set_ops` median, same workload, same machine, one fix at a time):

| Stage | Median (ms) | vs C++ twin |
|---|---|---|
| as first measured | 46,752 | 647x slower |
| + `first` cursor (§6.1) | 26,640 | 396x |
| + tombstone delete (§6.2) | 23,353 | 373x |
| + hash membership (§6.3) | **86.1** | **1.3x** |

Total: **543x**, ending at hashing speed (the twin's `std::set` is an
O(log n) red-black tree; Pentest sets are O(1) open-addressed hashes).

Also measured: moving `pt_guard` (one call per guarded variable read) and
`pt_truthy` (one call per loop condition/boolean operator) to
`static inline` in `runtime/pentest_rt.h` — 3 of while_int's 8 external
calls per iteration disappear. Effect: **11–24% on method/dispatch-heavy
programs, consistently retained across runs** (text_ops 449→341, closure_ops
282→235, dispatch_ops 570→488, coll_mixed 310→275 medians), **no measurable
change on the pure-arith loops** (inside the ±9% machine band): the inlined
truthiness switch runs on a dynamically tagged extern result and cannot
fold, so its branches roughly pay for the call it replaced. Collection
truthiness delegates to `pt_truthy_obj` (one extern call) because
`struct pt_obj` stays private to the runtime translation unit.

## 7. Findings and next optimizations

- **Loop counters.** Strength-reducing provably-int counters to native C
  `int64_t` (boxing only on escape) removes the per-iteration
  guard/add/re-box triple; the largest single remaining loop cost.
- **Guard elision.** Definite-assignment dataflow in the compiler could
  skip `pt_guard` for reads provably preceded by an assignment on every
  path (the unset-read diagnostic keeps firing for the cases the analysis
  cannot prove); removes 2 of 8 external calls on typical loops.
- **Static bool-condition truthy elision.** Contract: comparison
  operators always yield bool. Codegen could emit `(...).as.b` for
  conditions whose operand is a comparison, skipping `pt_truthy`'s switch
  entirely — the reason the §6 inlining did not move the loop cases.
- **GC (Stage 2C).** The no-GC leak policy is the whole RSS story:
  dispatch_ops 344 MB (≈1.1 KB leaked per kwargs-bound call: argument
  vectors + kwargs maps), coll_mixed 166 MB, closure_ops 119 MB (closure
  records + captured cells), text_ops 89 MB (concat/replace/split
  intermediates), while_string 44 MB. Every non-leaking case sits at the
  12 MB floor with the twins.
- Runtime ratios on scalar loops (155x int / 25x float) remain the dynamic-
  dispatch tax: every operation is an externally visible tagged-value call;
  the optimizations above shrink the *number* of calls, and 2C's GC removes
  the RSS costs, but single-step parity with C++ is not the design target —
  collection-level parity is (set_ops 1.3x, map_ops 3.6x, list_ops 6.0x).

## 8. Reproducing

```
bash bench/run-m2b.sh          # regenerates cases, builds with build/pentest, verifies, measures (~8 min)
BENCH_REBUILD=1 bash bench/run-m2b.sh   # force recompiles + re-measure compile times (~8 min)
```

- Uses the current `build/pentest` (the M1 harness `bench/run.sh` + frozen
  `bench/tools/pentest-m1` remain untouched for baseline reproducibility).
- Prerequisites: `clang`/`clang++`, `python3`, `taskset` (optional),
  bash, GNU coreutils, `awk`.
- Every run re-verifies byte-identical outputs for all 10 pairs and aborts
  on any mismatch. The before/after table is parsed from
  `bench/results/m1-baseline.md` when present.
- Case parameters live in `bench/gen-m2b.py`; the `while_*` twins share the
  M1 twins' constants so the paired rows stay exact.

## 9. Scope statement

These are **M2-2B numbers**: fully dynamic tagged values, real loops and
branches, closures/kwargs dispatch, hashing collections, no GC (all heap
objects leak until 2C), Linux x86_64 only. They characterize the 2B codegen
+ runtime against both the C++ twins (same algorithm, same output bytes)
and the frozen M1 baseline (same workloads, chains→loops). Stage 2C
(classes, exceptions, GC) will re-record the leak-driven RSS rows; the
loop-cost findings above name the codegen optimizations that would shrink
the remaining scalar-loop ratios.
