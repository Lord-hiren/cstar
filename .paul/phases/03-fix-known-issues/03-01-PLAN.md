<objective>
## Goal
Make the in-place text append (which already exists) apply to the way real code builds text: inside a function,
with the result returned, printed or tested afterwards. Today any such use disables it and the loop goes
quadratic. Close known issue #9 with a regression check that proves the fast path fires.

## Purpose
Servers and tools build text inside functions — exactly the case that is quadratic today. Measured on this
tree (2026-11-06, WSL):

| Loop | 100k appends | 400k appends |
|------|--------------|--------------|
| top-level global `s += "x"` (the known-issue repro) | 0.007 s | 0.009 s — already amortized |
| inside a function, then `return s` | 0.28 s | 4.9 s — **quadratic** |
| `parts.append` + `"".join` | 0.007 s | 0.018 s |

## Output
- A wider ownership proof in `analyze_text_cats` (no runtime change)
- Regression case `txt_build_amortized` and harness check `text_build_grow`
- Issue #9 closed; the eligibility rules documented
</objective>

## What the survey established (2026-11-06)
- The runtime already appends in place, with capacity doubling (`cs_text_cat_grow`). The codegen admits a statement
  `name = name + e` / `name += e` only when the slot provably owns its buffer. The writes rule accepts only literals
  and the candidates; structural rules exclude params, cells, pinned and name-table slots.
- **The blocker is the reads rule:** a read of the slot is allowed only as the append's own operand or `len(s)`.
  `return s`, `print(s)`, `if s.ends_with(",")`, `s == ""` all disqualify the slot.
- **Why reads matter, and why these are safe:** an in-place append writes past the slot's current length. Bytes
  any other value can see never change, so the only real hazard is a second appender on the same buffer. Checked:
  - `is` on text compares pointer **and** length, so an alias stops being identical after an append, as with copying;
  - every C-string consumer (`cs_text_cstr`, `cs_parse_float_text`) checks `p[len] == '\0'` at run time and copies
    when it isn't — interior slices already exist;
  - the code-point memo binds on (pointer, length, generation);
  - text `+` always allocates (`cs_add` → `cs_concat`), so `+` never returns an operand's buffer.
- **Two read classes are therefore safe:**
  - **terminal** reads: no append to the same slot can follow them in the same activation, so any alias they
    create never sees an append;
  - **non-retaining** reads: their result cannot reference the buffer (bool/int/None results, or a fresh copy).

## AC-1: Function-local builders are amortized
```gherkin
Given a function that builds text with s += x / s = s + x in a loop and then returns, prints or otherwise uses s
  after the loop (and may test s inside the loop with len, comparisons, in, truthiness, find, starts_with,
  ends_with, or print it)
When  it is compiled
Then  every such append compiles to cs_text_cat2(…, 1)
And   400k appends in a function run in well under 0.1 s (today 4.9 s); the global case stays as fast as today
```

## AC-2: Sharing patterns keep copy semantics
```gherkin
Given a slot whose value escapes (t = s, f(s), a container, a closure) and is appended again afterwards in the same
  activation

  the append
And   writes, params, captured cells, pinned slots, name tables and `variable.` access are still excluded exactly
  as before
```

    In the text-cat analysis only:
    - **Positions.** Give every statement visited in the scan a pre-order index, and track the stack of enclosing
      loops (a `while` condition counts as inside its loop; a `for` iterable is outside it, the body inside), plus
      whether the code is inside a `try` that has a `finally` body. Record each candidate's (key, index, loops).
    - **Non-retaining reads (exempt anywhere)**, marked like `len(s)` is today, when the slot Var is:
      - a direct operand of a comparison, identity or membership operator (==, !=, <, <=, >, >=, is, is not, in,
        not in), an operand of and/or/not, or either operand of a `+` that is not the candidate itself (text `+`
        always copies);
      - a positional argument of print, len, bool, int, float or hash;
      - the receiver of .find / .starts_with / .ends_with;
      - the whole condition of if/elif/while (truthiness), or the condition of a ternary.
      The ternary's result branches are NOT exempt: they return the operand itself.
    - **Terminal reads.** Instead of failing on the spot, record every remaining read with (key, index, loops,
      in_return_outside_try_finally, top-level?). At validation a read is terminal when:
      - (local slot) it sits in a `return` expression not inside a try-with-finally; or
      - no candidate of the same key has index >= the read's index and none shares an enclosing loop with it.
      For global slots the second rule applies only if the read and every candidate of the key are in top-level
      code (a read or candidate inside any function keeps today's rule). Default-parameter expressions are never
      terminal. A non-terminal recorded read sets bad_read exactly as today.
    - Keep the writes rule, the structural rules, name tables and `variable.` exclusions unchanged.
    - Rewrite the soundness comment: the new read classes and why each cannot let a second appender share the
      buffer.
    Avoid: runtime changes, touching other analyses, admitting anything the old rule rejected for a reason other
    than reads.
